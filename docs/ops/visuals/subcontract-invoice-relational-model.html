How a subcontract becomes an invoice — and then a payable record.

For Brandon: the invoice is the billing-period record for one commitment. On the subcontract path, its financial shape comes from the subcontract SOV, while its payment status ultimately arrives from Acumatica.

How data moves

A practical billing pass

This shows the application flow, not a new set of tables.

01

Establish the commitment

Create the subcontracts record for the project and vendor, then establish its SOV rows.

02

Open the billing window

billing_periods supplies the project dates; invoice creation resolves an open period if none is sent.

03

Create the pay application

The invoice header receives its subcontract, period, status, and invoice number. Its line rows contain the billed amounts and retainage.

04

Approve, export, reconcile

The invoice can point to an Acumatica AP bill; the system projects applied checks into commitment_payments.

Important design boundaries and safeguards
  • One commitment per invoice: the schema requires exactly one of subcontract_id or purchase_order_id. This guide follows the subcontract branch; purchase orders use the parallel commitment path.
  • No direct SOV-line key on invoice lines: subcontractor_invoice_line_items has invoice_id only. It copies/uses financial fields such as description, budget code, scheduled value, work complete, materials stored, and retainage. Reconciliation is therefore by the invoice’s subcontract plus business fields/order—not by an enforced line FK.
  • Calculated fields stay in the database: invoice line total_completed_stored, balance_to_finish, and net_amount_this_period are generated Postgres columns. The API updates inputs and lets the database calculate the derived totals.
  • Payment truth is external: commitment_payments is a read-only projection from Acumatica AP checks. It is not the manual invoice-payment table; it is the payment record used by this subcontract invoice experience.
  • Subcontractor SOV submissions are not invoice lines: submission tables handle the subcontractor’s SOV review workflow and can point back to a source SOV item. They do not create a foreign-key bridge from an invoice line to that item.
